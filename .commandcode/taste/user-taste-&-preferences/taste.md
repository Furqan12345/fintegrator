# User Taste & Preferences
- Always push to GitHub after making changes. Confidence: 0.95
- Commit taste files to git so preferences are shared across machines. Confidence: 0.9
- Keep commits focused by excluding unrelated file changes from staged area before committing. Confidence: 0.75
- Investigate project setup files (docker-compose.yml, Dockerfile, launchSettings.json) before starting a project to understand configuration. Confidence: 0.85
- Start dependent services in dependency order (e.g. API before the client that consumes it) so the client can connect immediately on first request. Confidence: 0.85
- Verify a service is healthy (check /health endpoint or HTTP status code) before starting dependent services. Confidence: 0.85
- When a previously-seen error recurs (e.g., a server crashes on startup), continue autonomously by diagnosing the root cause and retrying (e.g. fix CWD/path, restart from the correct working directory) rather than stopping to ask the user. Confidence: 0.85
- Run long-lived servers in the background and report task IDs so they can be stopped later. Confidence: 0.8
- Stop background dev servers once verification work is complete (or when asked to pause) rather than leaving them running idle — keep them up during active verification, but clean them up afterward. Confidence: 0.8
- Use `dotnet run --project <path> --urls http://localhost:<port>` to start .NET servers with explicit port bindings. Confidence: 0.85
- Use `ping -n <seconds> 127.0.0.1 >nul 2>&1` as a Windows-compatible wait/sleep mechanism since `sleep` is not available in cmd.exe. Confidence: 0.85
- Remove dead/unused code as part of refactoring (e.g., remove methods that are no longer called after feature changes). Confidence: 0.85
- Prefer backward-compatible implementations: new features should preserve existing behavior for existing inputs (e.g., single-level paths keep existing flat-array output when wildcard paths add new behavior). Confidence: 0.8
- For N+1 fan-out patterns (e.g., get orders then per-order API calls for line items), prefer creating a new ForEach/iterator node type that fans out array elements into per-element subgraph executions, rather than embedding HTTP calls in mapping scripts or working around the limitation. Confidence: 0.85
- Commit messages use a structured format: a subject line, blank line, bullet-point body, ending with `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer. Confidence: 0.85
- Use `newTT` as the consistent feature branch name for all work and push to origin after every commit. Confidence: 0.85
- On Windows (cmd.exe), write commit messages to a temp file and use `git commit -F <file>` since heredocs (`<<EOF`) are not supported. Confidence: 0.8
- Store sample/demo integrations in `samples/integrations/` as JSON files with a companion `README.md` documenting the node map, data flow, and usage. Confidence: 0.8
- Seed sample/demo flows into the dev tenant's database (tenant ID `11111111-1111-1111-1111-111111111111`) idempotently at application startup so they are immediately visible and runnable from the UI. Confidence: 0.8
- After every code change, restart the affected dev server(s) and run a full-stack end-to-end verification before calling it done: API `/health` returns 200, the client serves its Blazor boot resources (`index` + `blazor.webassembly.js` + `dotnet.js`) with 200, and seeded/live data is reachable through the API using the dev API key. Never leave the API down or run a stale client during verification — a down API or stale client hangs the Blazor FlowDesigner on the loading screen. Confidence: 0.9
- For iterator/ForEach nodes, the fan-out vs. post-loop-merge routing split must be **declared by the user in the UI via a dedicated completion port** (an edge with `SourcePortId="completed"`), never inferred by the engine from topological heuristics like "first node with an external predecessor is the merge boundary." The user rejects routing that "looks hard coded at back end" and wants maximum UI control over control-flow intent. Confidence: 0.9
- Workflow edges must represent data/flow wiring, never hidden control signals: the user finds "control-as-data" wiring confusing (a spurious edge added only to force the engine's routing inference). Control-flow intent should be expressed explicitly (e.g. via a port id), not disguised as a data edge that misleads the diagram. Confidence: 0.85
- Do NOT use "restart the application/server" as the fix for recurring problems (e.g., loading screens, transient states). The user objects to this pattern across tasks ("What you do everytime? Just restart the application, nothing else") and wants the actual root cause diagnosed and fixed in code instead of papered over with a restart. Confidence: 0.9
- Architectural preference: all data/path resolution (e.g. `arrayPath`, iteration element bindings) must flow through a **single central flow state** rather than being stored as per-node configuration. The user explicitly rejects node-scoped path config ("why arrayPath in any of the node, is not getting from FlowState, when i told you earlier every path, or anything should be done through central flow state") and wants the engine to resolve path values from the shared state so routing/decisions stay centralized and inspectable, not hard-coded at the back end. Confidence: 0.85
- Wants `arrayPath` values to use the **explicit `flowState.<Node>.<path>` syntax** so the central-state sourcing is visually obvious, rather than relying on implicit/transitive resolution where the path "does not look like it getting from FlowState" even though the data does originate there. The user calls out configs that source from the flow state only transitively (via upstream `input` = `flowState[node]`) as not visibly demonstrating the intent. Confidence: 0.85
- Wants transparency about data provenance when discussing configs: the user asks whether a referenced path is mock/dummy test data or original/real data, and which specific card/component the configuration belongs to. Confidence: 0.7
- Read the agent handover doc first to build context before starting any work. Confidence: 0.9
- Write all future work in the agent handover doc for other agents, keeping it as the single source of truth for context. Confidence: 0.9
- Keep handover doc context compact and short — avoid context explosion; use brief summaries. Confidence: 0.9
- When asked about project state, build/test the project and report recent changes (commit history + build/test results). Confidence: 0.8
- When verifying that all cards/components work as specified, cross-reference the architecture doc, wireframes, card razor components, config classes, domain parsers, DTOs, the executor/engine, and existing integration tests — use existing integrations/tests to verify behavior rather than only reading code. Confidence: 0.85
- When issues are found during verification, create two agents: one to implement fixes and a second to independently verify that specifications are met. Confidence: 0.9
- The engine must honor all configuration values exposed by cards — if a card writes a config value (e.g. parallel execution, max degree of parallelism), the corresponding engine/executor component must read and use it. Never expose a config option in the UI that the engine silently ignores. Confidence: 0.85
- When adding parallel/concurrent execution, use explicit `lock` statements around shared mutable state (counters, HashSet/List/Dictionary collections, repository calls) rather than lock-free approaches. Confidence: 0.85
- When making test doubles thread-safe for concurrent scenarios, add locks around mutable collection access while preserving existing collection types and ordering assertions. Confidence: 0.8
- For parallel iteration in .NET, prefer `Parallel.ForEachAsync` with `ParallelOptions { MaxDegreeOfParallelism, CancellationToken }`. Confidence: 0.75
- UI node cards/components in the FlowDesigner should be collapsible/minimizable when they grow large with content, so users can collapse sections they don't need to see. The chevron toggle should not interfere with node dragging (stopPropagation) and should visually rotate when collapsed. Confidence: 0.85
